# agent-creance v0.1 — Technical Specification & Build Plan

This document turns [`docs/design.md`](../../../docs/design.md) into a buildable,
start-to-end plan for v0.1. It does **not** restate the design's rationale — read
the design first. Its job is decomposition: the components to build, the order to
build them in, what each one must satisfy to be "done," and the dependencies and
spike-gates between them, at a granularity where **each work package (WP) maps to
roughly one ticket**.

WP IDs (`WP-<phase>.<n>`) are stable handles so tickets can cite them. Spike IDs
(`S1`–`S5`) are the design's open spikes.

---

## 1. Scope and ground rules

**In scope (v0.1), from the design's roadmap:** core orchestration (Safehouse
invocation, mitmproxy lifecycle with refcounting), `network.sb` + `policy.json`
compilation, two generators (`package_json`, `composer_json`), per-host
enforcement modes (`intercept`/`passthrough`), three-response-type enforcement,
skill install, `allow`/`deny`/`policy` commands, JSONL audit log with rotation,
CA bootstrap with post-install verification, prerequisite check with
tested-version warnings, `doctor`, process-group signal forwarding.

**Explicitly deferred (do not build in v0.1):** secret injection / `op://`,
DNS-resolver blocklists, Haiku-as-judge, additional ecosystem generators,
per-generator options, config-driven process plugins, non-Claude agents,
file-based credential support (detect-and-refuse only — see WP-4.1),
executable-config isolation / the config cage (v0.1 mounts the real `~/.claude`
read-write so the host login works out of the box — revisit in **AC-0046**).

**Conventions every WP inherits** (from `CLAUDE.md` / `.claude/tce/profile.md`):

- No logic package calls the OS directly. New side-effecting dependencies get a
  new `internal/sysdep` interface + a fake in `sysdep/sysdeptest`, injected via
  the `cli.App` composition root. See WP-1.4.
- Pure logic → table tests. Generated artifacts (`.sb`, `policy.json`, reports,
  403 bodies) → golden tests with `-update`. CLI behaviour → hermetic
  `testscript` `.txtar`. External tools (`agent-safehouse`, `mitmproxy`,
  `security`) only under `//go:build integration`.
- Security-critical runtime state stays out-of-tree in
  `~/.cache/agent-creance/`. Never mount it into the cage.

## 2. Current state (the starting line)

- `internal/cli`: `version` and `doctor` commands (doctor currently does the

## 4. Cross-cutting concerns (decide once, apply everywhere)

These are not tickets on their own but constrain many WPs; call them out in each
relevant ticket.

- **C1 — Go↔Python matcher parity (highest-risk duplication).** The
  allow/soft-deny/hard-deny + mode decision logic exists **twice**: in Go for
  `policy explain` (WP-2.1) and in Python for runtime enforcement
  (`enforcer.py`, WP-3.1). They must never disagree, or `explain` lies about what
  the proxy will do. **Mitigation:** a single language-neutral corpus of
  `(ruleset, url, method) → expected decision+mode` vectors in
  `testdata/decision-vectors/`, consumed by *both* the Go table tests and the
  Python addon tests. No decision-logic WP is "done" without adding vectors.
- **C2 — sysdep seam growth.** New OS touchpoints — Keychain, clock, filesystem,
  `flock`, process-group/signals — each become a small `sysdep` interface + fake
  *before* the consuming logic is written (WP-1.4 seeds them).
- **C3 — Golden everything generated.** `.sb`, `policy.json`, the three 403 JSON
  bodies, `policy show` output, `doctor`/report output — all golden-tested with
  `-update`; review diffs (`make golden`).
- **C4 — Out-of-tree invariant.** Any WP that writes runtime state asserts it
  lands under `~/.cache/agent-creance/projects/<hash>/` and is never added to the
  cage's mounted dirs. Worth a dedicated test per writer.
- **C5 — Spike gating.** WPs marked with a spike must not merge enforcement code
  ahead of the spike's resolution; they may merge scaffolding/tests behind it.

## 5. Phase 0 — Spikes (gating, do first)

Each spike is a timeboxed investigation ticket producing a findings note under
`thoughts/shared/research/` and a decision. They gate the WPs listed.

| WP | Spike | Question | Gates |
|---|---|---|---|
| WP-0.1 | **S1** | Does the agent/toolchain accept the mitmproxy CA for `api.anthropic.com`, npm/PyPI, `github.com`? Decides the shipped default `mode` for `api.anthropic.com` (`intercept` if it works, `passthrough` if Claude pins). | WP-3.1, WP-5.1, baseline config |
| WP-0.2 | **S2** | Can a `sandbox-exec` process read+refresh the Anthropic Keychain item without prompts? Concurrent-refresh safe? Exact service/item name + ACL? | WP-4.1, WP-4.2 |
| WP-0.3 | **S3** | Do `(remote tcp "127.0.0.1:N")` allows genuinely refuse non-allowlisted localhost ports over **both** v4 and v6 with one family pinned? | WP-2.5, WP-3.4 |
| WP-0.4 | **S4** | Do Claude Code, `npm`, `pip`, `git`-over-HTTPS, `go` all honour `HTTPS_PROXY`? | WP-4.2 |

passthrough-only for Anthropic, or generated-full-profile instead of append)
folded into the design before the dependent phases start.

## 6. Phase 1 — Foundations

No external tools; pure logic + the testability seam. Fully hermetic.

- **WP-1.1 — State directory & project identity** (`internal/state`). Canonical
  absolute-path resolution (`realpath`), the path→`<hash>` scheme shared by the
  lock file and state dir, and the directory layout (`projects/<hash>/` with
  `policy.json`, `network.sb`, `proxy.lock`, `egress.jsonl`, `claude/`,
  session-overlay). Pure + filesystem seam.
  *Done when:* given a path, returns a stable hash + resolved layout; symlinked
  aliases collapse to one identity; table-tested.
- **WP-1.2 — Config schema & loader** (`internal/config`). Go structs for the
  full `.agent-creance.yaml` schema (agent, safehouse, network.host_services,
  network.egress.{generators,allow,deny_always}, env, include), incl. the
  per-rule `mode` field; parse + structural validation with actionable errors.
  *Done when:* the design's example config round-trips; invalid configs produce
  golden error messages; `mode: passthrough` with `paths`/`methods` is rejected
  (per Per-host modes). Table + golden.
- **WP-1.3 — Include resolution & merge** (`internal/config`). Implicit global
  (`~/.config/agent-creance.yaml`), recursive `include:` with cycle detection +
  depth limit, scalar-override + `allow`/`deny_always` list-union semantics.
  *Done when:* layered fixtures merge per spec; cycles/over-depth error cleanly.
  Table-tested.
- **WP-1.4 — sysdep seam extensions** (`internal/sysdep` + `sysdeptest`).
  Interfaces + fakes for the OS touchpoints later phases need: `Clock`,
  `FileSystem`, `Keychain`, `Flock`, `ProcessGroup`/signals. Ship the interfaces
  and fakes now (C2); real impls land with their consumers.
  *Done when:* each interface has a fake; compile-time `var _ Iface` assertions
  in place.

## 7. Phase 2 — Policy & profile compilation

The first user-visible value, all hermetic/golden-testable, no proxy yet.

- **WP-2.1 — Rule model & matcher** (`internal/policy`). Host (incl. `*.` and
  `*` wildcards), path-prefix + `**`/`*` glob, method, and `mode` matching;
  precedence (`deny_always` shadows `allow`; unmatched → soft-deny). Establishes
  the **C1 decision-vector corpus**.
  *Done when:* every vector in `testdata/decision-vectors/` passes; table-tested.
- **WP-2.2 — Registry clients & metadata cache** (`internal/generator/registry`).
  npm (`registry.npmjs.org`) + Packagist HTTP clients; per-package cache at
  `~/.cache/agent-creance/registries/<registry>/<package>.json` (30-day lazy
  refresh). Unit-tested against a fake HTTP transport; live calls
  integration-tagged.
- **WP-2.3 — Generators** (`internal/generator`). `package_json` + `composer_json`:
  direct-deps walk, homepage rule (host-wide vs path-scoped for shared hosts),
  repository rule scoped to `<org>/<repo>`, the **forge content-host table**
  (GitHub: `raw.`/`codeload.`/`<org>.github.io`/`objects.githubusercontent.com`),
  manifest-hash output cache, rule-source annotation. Trust model: registry
  fields verbatim.
  *Done when:* fixture manifests produce golden rule sets incl. forge companions;
  missing homepage/repo emit nothing.
- **WP-2.4 — Policy compiler** (`internal/policy`). Union explicit + generated +
  included + global + session-overlay → `policy.json`; **input-hash cache**
  (skip regeneration when inputs unchanged); each rule annotated with its source.
  Inputs hash includes manifests + overlay (per design).
  *Done when:* golden `policy.json`; unchanged inputs are a cache hit; out-of-tree
  write asserted (C4).
- **WP-2.5 — Seatbelt profile compiler** (`internal/profile`). `deny network*`
  baseline + `host_services`→`127.0.0.1:<port>` allow rules + the **launch-time
  proxy-port fragment** (regenerated each launch from the live port; *not* part
  of the input-hash cache). Gated **S3, S5**.
  *Done when:* golden `.sb` for host-service fixtures; port fragment is generated
  separately from a supplied port; IPv4 literal enforced.
  > **Correction (AC-0014, 2026-06-05):** per resolved spikes S3/S5 the literal
  > `127.0.0.1:<port>` rule form does **not** compile ("host must be `*` or
  > localhost"). The compiler emits `(remote tcp "localhost:<port>")` (covers v4+v6,
  > port-enforced) and never `*:N`; "IPv4 literal enforced" is replaced by "localhost
  > token, never a literal IP". `network.sb` is also not input-hash cached at all
  > (regenerated every launch) — see the AC-0014 plan/research.
- **WP-2.6 — `policy show` / `policy explain`** (`internal/cli`). Render the fully
  resolved policy with `[explicit]`/`[generated:…]`/`[global:…]` annotations and
  a distinct flag for `passthrough` rules; `explain URL` reports the matching rule
  + source. Uses WP-2.1 matcher (C1).
  *Done when:* `testscript` + golden output match the design's sample.
- **WP-2.7 — `policy refresh`** (`internal/cli`). Force registry re-fetch
  (invalidate per-package cache). Small.

**Milestone M1 — "Policy visible":** `agent-creance policy show`/`explain`
produce correct annotated output from a real project config (with generators),
fully offline against cached metadata. No external tools required.

## 8. Phase 3 — Proxy enforcement & audit

Introduces the Python addon and the lifecycle. Live behaviour is
integration-tested; logic is unit-tested with fakes.

- **WP-3.1 — `enforcer.py` decision engine** (`internal/proxy/enforcer`). Load
  `policy.json`; emit the three response types (allow / soft-deny 403 +
  `X-Cage-Reason: soft-deny` + JSON body / hard-deny 403 + reason); implement
  per-host **modes** incl. `passthrough` (CONNECT tunnel, no TLS termination,
  host-only allow, deny-at-CONNECT still enforced); mtime-poll **hot reload**.
  Gated **S1**. Must pass the C1 decision vectors from the Python side.
  *Done when:* vectors pass; integration test shows allow/soft/hard + passthrough
  against a live mitmproxy; golden 403 bodies.
- **WP-3.2 — Audit JSONL writer** (in `enforcer.py`). Per-request entry
  (timestamp, method, URL, decision, matching rule, status; host-only for
  passthrough), `0600`, sensitive-header redaction, 500 MB rotation
  (delete `.1`, rename current→`.1`, fresh current).
  *Done when:* entries match schema golden; redaction verified; rotation flips at
  threshold without dropping entries.
- **WP-3.3 — Embed & extract** (`internal/proxy`). `go:embed` the addon; extract
  to the state dir on first run (constant, not per-project); version/refresh on
  binary change.
  *Done when:* extraction is idempotent; out-of-tree (C4).
- **WP-3.4 — Proxy lifecycle manager** (`internal/proxy`). Lock-file schema
  (proxy PID, port, policy hash, attached-agent PIDs); `flock` RMW; prune dead
  PIDs (`kill -0`); start-vs-attach; ephemeral `:0` allocation recorded to lock;
  **best-effort port reclaim on restart**; teardown refcount decrement killing
  the proxy only when the agent array empties; **session-overlay purge on
  last-agent-exit**; the **port-changed-under-attached-agents warning** (never
  kill agents). Gated **S3**.
  *Done when:* concurrent attach/detach modelled with fakes; reclaim-success and
  reclaim-fail (warn) paths covered; integration test with real mitmproxy.
- **WP-3.5 — Audit log reader** (`internal/audit`). `logs --follow` via `fsnotify`
  (rotation-aware, not `tail -f`); `logs --summary` reading `.1`+current as one
  stream.
  *Done when:* follow survives a rotation mid-stream; summary aggregates both
  files. `testscript` + unit.

**Milestone M2 — "Egress enforced":** a manually-started proxy enforces a
compiled policy against live HTTP(S), returns the three structured responses,
honours passthrough, hot-reloads on `policy.json` change, and writes a rotating
audit log. (Integration milestone; not yet wired to `run`.)

## 9. Phase 4 — Cage integration & `run`

Ties policy + proxy + Safehouse + credentials into the headline command.

- **WP-4.1 — Credential detection** (`internal/cred` + `sysdep.Keychain`). Detect
  the Anthropic Keychain item (service/name from S2); if absent but a file-based
  `~/.claude/.credentials.json` exists, **refuse with the clear message** (file
  creds out of scope for v0.1). Gated **S2**.
  *Done when:* keychain-present → proceed; file-only → refuse with the documented
  message; neither → point at host `claude` login.
- **WP-4.2 — Safehouse invocation** (`internal/cage`). Build `--add-dirs*` /
  `--enable` / `--append-profile` (WP-2.5 output) / `--env-pass`; inject env
  (`HTTPS_PROXY`, CA paths: `NODE_EXTRA_CA_CERTS`/`SSL_CERT_FILE`/
  `REQUESTS_CA_BUNDLE`/`GIT_SSL_CAINFO`). **v0.1 mounts the real `~/.claude`
  (and `~/.claude.json`) read-write and does *not* redirect `CLAUDE_CONFIG_DIR`**
  — the config cage is deferred (AC-0046), so the caged agent uses the host's
  Claude config + login as-is. (The originally-specified ephemeral
  `CLAUDE_CONFIG_DIR` redirect with a sanitized seed is the target design
  AC-0046 will restore.) Gated **S4, S5**.
  *Done when:* the constructed argv+env match golden for a fixture config;
  integration test launches Safehouse with a trivial caged command.
- **WP-4.3 — Process group & signal forwarding** (`internal/cage` +
  `sysdep.ProcessGroup`). New process group (`Setpgid`); forward SIGINT/SIGTERM
  to the whole group; wait-for-group before the lock decrement (deterministic
  teardown ordering).
  *Done when:* Ctrl-C tears down a spawned child tree in an integration test; unit
  test asserts forwarding via the fake.
- **WP-4.4 — `run` command** (`internal/cli`). Orchestrate: prereq check →
  setup-precondition check (trusted CA + skill present, else point at `setup`) →
  state resolve → compile (cache-aware) → proxy start/attach → cage exec →
  trapped teardown. Blocks; refcount on exit.
  *Done when:* `testscript` with stubbed `agent-safehouse`/`mitmproxy` drives the
  full happy path + the "setup not run" refusal; integration smoke launches a
  real caged `claude --version`-style command.
- **WP-4.5 — Adversarial cage verification harness** (capstone). A hostile "fake
  agent" payload run *inside the real cage* via `run`, exercising the full
  `docs/design.md` "What the cage prevents — and what it doesn't" matrix with
  three assertion classes — **BLOCKED** (host-file reads, raw TCP bypass,
  non-allowlisted localhost port over v4+v6, child-process inheritance, soft/hard
  deny, direct DNS), **ALLOWED** (false-negative guard: allowlisted egress,
  generated-rule host, `host_services`, passthrough-validates-real-cert), and
  **DOCUMENTED** (honesty: `rm` within `./` succeeds, exfil via an allowlisted
  POST is possible + audited; **in v0.1 planted config *does* persist** — the
  real `~/.claude` is mounted read-write, so this vector documents the deferred
  config cage rather than asserting non-persistence; see AC-0045/AC-0046).
  Includes a
  **negative control** that *fails* the battery against a weakened cage, a
  coverage check binding each assertion to a design bullet, and a checked-in
  human red-team checklist for un-automatable vectors. Gates M3 sign-off; the
  piecemeal isolation checks in WP-2.5/3.1/4.2/4.4 fold into it.
  *Done when:* `make test-integration` runs the battery green; the negative
  control is red against a weakened profile; every threat-model bullet maps to a
  labelled assertion.

**Milestone M3 — "Caged run":** `agent-creance run` (after `setup`) launches the
agent inside Safehouse with the proxy in front, enforcing policy, logging egress,
cleaning up on exit and on Ctrl-C. **This milestone is not signed off until the
WP-4.5 adversarial battery (AC-0033) is green** — the cage's confinement claims
must be tested, not assumed. This is the v0.1 headline.

## 10. Phase 5 — Setup & onboarding

- **WP-5.1 — CA bootstrap + verification** (`internal/setup`). Generate the
  mitmproxy CA if absent; `security add-trusted-cert` into the login keychain;
  **post-install live verification** (short-lived proxy on a random port,
  `curl https://example.com` through it, validate the chain) with an explicit
  error on the silent-cancel failure mode. Gated **S1**. Integration.
- **WP-5.2 — Skill install** (`internal/setup`). `go:embed` `SKILL.md`; install to
  `~/.claude/skills/agent-creance/`; `--no-skill` opt-out. Never touch project
  `CLAUDE.md`.
- **WP-5.3 — `setup` command** (`internal/cli`). Wire 5.1 + 5.2; `--no-ca-install`
  (env-var-only mode, with the best-effort-coverage caveat for tools that don't
  honour the CA-bundle env vars).
- **WP-5.4 — `init` command** (`internal/cli`). Write the `.agent-creance.yaml`
  template; detect `package.json`/`composer.json` and pre-populate `generators:`.
  *Done when:* `testscript` shows template emission + manifest-driven generator
  prepopulation.

## 11. Phase 6 — Mutation commands & operational hardening

- **WP-6.1 — `allow` / `deny`** (`internal/cli`). Append soft-allow to project
  YAML; `--global` (to `~/.config`); `--once` (write to the **session-overlay**,
  purged per WP-3.4); `deny … --reason`. Re-compile + hot-reload after mutation.
  *Done when:* each variant lands in the right file; `--once` survives only the
  session; YAML edits preserve comments/structure where feasible.
- **WP-6.2 — `doctor` extension** (`internal/cli`, *extend*). Add CA live-verify
  (reuse WP-5.1), orphan-proxy scan, exposed-host-service scan, flock-unreliable
  filesystem warning (iCloud/SMB), and the port-changed-under-attached-agents
  condition; keep the existing version report (highlight every mismatch incl.
  patch). `--fix` auto-remediates what it can.
  *Done when:* golden report covers each condition; `--fix` cleans an orphan proxy
  in an integration test.
- **WP-6.3 — `status` / `clean`** (`internal/cli`). `status`: running cages across
  all projects (read every lock). `clean`: tear down this project's proxy + lock +
  overlay; orphan-safe.
  *Done when:* `status` lists fixtures; `clean` is idempotent and purges overlay.

**Milestone M4 — "v0.1 complete":** full command surface, multi-agent shared
proxy, onboarding (`setup`/`init`), policy mutation, audit tooling, and `doctor`
diagnostics all green under `make test`; integration suite green under
`make test-integration`.

## 14. Open risks carried into the build

- **Spike outcomes can reshape WP-2.5 / WP-3.1 / WP-4.2.** If S5 fails,
  `--append-profile` narrowing is replaced by a fully-generated profile (WP-2.5
  grows). If S1 shows pinning, `api.anthropic.com` ships `passthrough` and WP-3.1's
  passthrough path becomes load-bearing rather than optional.
- **C1 (Go↔Python matcher parity)** is the most likely source of subtle bugs;
  the shared decision-vector corpus is the guardrail and must precede both
  implementations.
- **Proxy crash recovery** is decided (warn + never kill; best-effort port
  reclaim) — WP-3.4 must implement the *warning + doctor/status surfacing*, not
  just the reclaim.
- **File-based credentials** are detect-and-refuse only (WP-4.1); a real
  implementation is out of v0.1 scope.
