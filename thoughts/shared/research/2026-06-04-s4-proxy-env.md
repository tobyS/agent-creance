# Spike S4 — Proxy-env-var coverage across the toolchain

**Decision: all five tools route through `HTTPS_PROXY` — but the CA-trust story splits
in two. `claude`/`npm`/`pip`/`git`-over-HTTPS honor the belt-and-suspenders CA env vars
(`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO`) and work
with the mitmproxy CA supplied purely via env. `go` is the outlier: it honors
`HTTPS_PROXY` (proven — it dials the proxy and mitmproxy connects upstream to
`proxy.golang.org` on its behalf), but on macOS it IGNORES `SSL_CERT_FILE` and every
other CA-bundle env var and consults only the system keychain. So `go` only succeeds
through the cage when the mitmproxy CA is installed in the login/system keychain — which
`agent-creance setup` does by default (design line 427). The env-var-only fallback
(`setup --no-ca-install`, line 357) is INCOMPATIBLE with `go`. No `GOPROXY`/`GONOSUMDB`
tweak is needed: default `GOPROXY=proxy.golang.org,direct` + `GOSUMDB=sum.golang.org`
both route via `HTTPS_PROXY`, so the only `go`-specific requirement on AC-0017's allowlist
is that BOTH `proxy.golang.org` AND `sum.golang.org` are allowed (or `GOSUMDB=off` if an
operator declines the checksum DB). `git`-over-SSH stays unsupported by design (SSH cannot
traverse an HTTP proxy).**

## Question

Under the deny-all network baseline the cage's only egress is the proxy, reached via
`HTTPS_PROXY`. Any tool the agent uses that ignores `HTTPS_PROXY` hard-fails. Confirm the
real toolset — Claude Code, `npm`, `pip`, `git`-over-HTTPS, `go` — all honor it and route
through mitmproxy, and document any that need an extra/alternate env var or don't route at
all. This decides the exact env set AC-0023 (WP-4.2) injects into the caged agent. See
`docs/design.md` "Open spikes" (S4, line 22) and "The proxy and the credential story"
(line 427, the belt-and-suspenders CA env vars). Open question carried from the ticket:
does `go` need `GOPROXY`/`GONOSUMDB` tweaks, or does `HTTPS_PROXY` suffice?

## Environment

| Tool | Version |
|---|---|
| macOS | 26.5 (build 25F71), Darwin 25.5.0, arm64 |
| mitmproxy / mitmdump | 12.2.3 |
| claude (Claude Code) | 2.1.162 |
| npm | 11.16.0 (Node) |
| pip | 26.1.1 (Python 3.14, invoked as `pip3`) |
| git | 2.50.1 (Apple Git-155) |
| go | 1.26.4 darwin/arm64 |
| curl | 8.7.1 (control) |

The mitmproxy CA at `~/.mitmproxy/mitmproxy-ca-cert.pem` was supplied to the tools via the
agent-creance env set ONLY. It was confirmed **absent from both the login keychain and the
System keychain** (`security find-certificate -c mitmproxy` → 0 matches in each). That
absence is load-bearing for this spike: it means any tool that succeeded through the proxy
did so because of the **env-var CA**, not pre-existing system trust — and lets the `go`
result (failure) be attributed cleanly to `go` ignoring those env vars.

## Method

`mitmdump -p 18080 -w flows.mitm --set flow_detail=1` ran as a host daemon, logging every
flow. Each tool ran with `HTTPS_PROXY=HTTP_PROXY=http://127.0.0.1:18080` and the CA env set
(`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, `GIT_SSL_CAINFO` → the CA),
then the proxy log was inspected for a matching `server connect <host>:443` (the
authoritative "mitmproxy opened the upstream connection on this client's behalf" =
routed-through-proxy signal). For each tool a **negative control** (run with the CA env
unset) confirmed the request still reached the proxy and failed at TLS — proving both that
the tool routes through the proxy AND that the env-var CA (not system trust) is what makes
it succeed. For `go`, extra controls (dead proxy port; direct-with-CA-only) isolated the
proxy-honoring question from the CA-trust question.

## Results

### Authoritative routed-through-proxy host list (`server connect` lines)

Every tool's upstream host appears, proving each routed through mitmproxy:

```
server connect api.anthropic.com:443          (claude)
server connect mcp-proxy.anthropic.com:443    (claude startup — incidental)
server connect http-intake.logs.us5.datadoghq.com:443  (claude telemetry — incidental)
server connect registry.npmjs.org:443         (npm)
server connect pypi.org:443                   (pip)
server connect files.pythonhosted.org:443     (pip)
server connect github.com:443                 (git over HTTPS)
server connect proxy.golang.org:443           (go)
```

### 1. Claude Code — **PASS**

`HTTPS_PROXY=… NODE_EXTRA_CA_CERTS=$CA SSL_CERT_FILE=$CA claude -p "Reply … pong"` →
printed `pong`, exit 0. Proxy log: `POST … api.anthropic.com` plus the startup calls. CA
via the Node env vars; nothing pinned (re-confirms S1). **Routes via `HTTPS_PROXY`; CA via
`NODE_EXTRA_CA_CERTS`/`SSL_CERT_FILE`.**

### 2. `npm` — **PASS**

`npm view react version` → `19.2.7`, request to `registry.npmjs.org` in the log. Negative
control (CA env unset, forced online with a fresh cache) →
`UNABLE_TO_VERIFY_LEAF_SIGNATURE … unable to verify the first certificate`. So npm reaches
the proxy and **needs `NODE_EXTRA_CA_CERTS`**. `npm config`: `strict-ssl=true`, no
`cafile`, no `proxy`/`https-proxy` — so routing was driven purely by the `HTTPS_PROXY`
env var, not npmrc. (Caveat captured: a *second* identical `npm view` with no CA env
"succeeded" only because it was served from npm's local `_cacache` — there was just one
`registry.npmjs.org/react` request in the proxy log. Cache hits can mask a broken egress
path; the online control is the real test.) **Routes via `HTTPS_PROXY`; CA via
`NODE_EXTRA_CA_CERTS`.**

### 3. `pip` — **PASS**

`pip3 download --no-deps requests -d …` → `Saved …/requests-2.34.2-…whl`, requests to
`pypi.org` (`/simple/requests/`) and `files.pythonhosted.org` in the log. Negative control
(CA env unset) → `SSLCertVerificationError('… "pypi.org" … not trusted')`, retrying. So pip
reaches the proxy and **needs `REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`** (pip's default certifi
bundle excludes the mitmproxy CA). **Routes via `HTTPS_PROXY`; CA via
`REQUESTS_CA_BUNDLE`/`SSL_CERT_FILE`.**

### 4. `git` over HTTPS — **PASS**

`git ls-remote https://github.com/golang/go` → ref list returned; `github.com`
`/info/refs?service=git-upload-pack` + `POST /git-upload-pack` in the log. Negative control
(`GIT_SSL_CAINFO` unset) → `fatal: … SSL certificate problem: unable to get local issuer
certificate`. So git reaches the proxy and **needs `GIT_SSL_CAINFO`** — even Apple Git
(Secure Transport build) honored the env-var CA path here. **Routes via `HTTPS_PROXY`; CA
via `GIT_SSL_CAINFO`.** (`git`-over-SSH not tested — unsupported by design; see Decision.)

### 5. `go` — **PASS (routing); CA only via system keychain** — the headline finding

`go env`: `GOPROXY=https://proxy.golang.org,direct`, `GOSUMDB=sum.golang.org` (defaults).
Three controls separate the two axes:

| Control | Setup | Result | What it proves |
|---|---|---|---|
| **A** | `HTTPS_PROXY=http://127.0.0.1:9` (dead port) | `proxyconnect tcp: dial tcp 127.0.0.1:9: connect: connection refused` | go **honors `HTTPS_PROXY`** — it dials the configured proxy |
| **B** | live proxy `:18080`, no CA env | `tls: failed to verify certificate: x509: "misc-sni.google.com" certificate is not trusted` | go reaches the proxy, **rejects the MITM cert** (CA not in system store) |
| **C** | no proxy, no CA env | success (full version list) | direct path works via system trust (baseline) |
| **D** | no proxy, `SSL_CERT_FILE`=mitmproxy-CA-only | **success** (real Google cert accepted) | go **IGNORES `SSL_CERT_FILE`** — had it honored it, the real cert would have been rejected |

The proxy log corroborates routing directly: `server connect proxy.golang.org:443` followed
by `Client TLS handshake failed. The client does not trust the proxy's certificate for
proxy.golang.org (ssl/tls alert bad certificate)`. mitmproxy opened the upstream connection
**on go's behalf** (= routed through the proxy), and go terminated the handshake because the
mitmproxy CA is untrusted. (The `misc-sni.google.com` CN in the client error is just
mitmproxy's upstream-sniffed cert name for the Google frontend.)

Reconciling A + D: go honors `HTTPS_PROXY` but **does not consult `SSL_CERT_FILE` (or any
CA-bundle env var) on macOS** — it uses the macOS platform verifier (system keychain) only.
Therefore `go` succeeds through the cage **iff the mitmproxy CA is trusted in the
login/System keychain**. `agent-creance setup` installs it there by default (design line
427), so the headline `run` works; the **`setup --no-ca-install` env-only path breaks
`go`**.

**Open question answered:** no `GOPROXY`/`GOSUMDB`/`GONOSUMDB` tweak is required for
*routing* — `HTTPS_PROXY` suffices and the default `proxy.golang.org` (and `,direct`
fallback, and `sum.golang.org`) all traverse the HTTP proxy. The only requirement `go`
places on the egress allowlist is that **both `proxy.golang.org` and `sum.golang.org`** are
allowlisted (a real `go get`/`go mod download` contacts the checksum DB in addition to the
module proxy). If an operator chooses not to allowlist `sum.golang.org`, `GOSUMDB=off` is
the documented alternative — optional, not required.

## Answers to the ticket's acceptance criteria

- Research note exists at `thoughts/shared/research/2026-06-04-s4-proxy-env.md` — **yes**.
- PASS/FAIL recorded for Claude Code / `npm` / `pip` / `git` (HTTPS) / `go` — **all PASS for
  proxy routing** (§1–§5); `go` carries a CA-trust caveat (system keychain only).
- Any tool needing an extra/alternate env var documented — **yes**: per-tool CA env vars
  differ (Node vs Python vs git), and `go` needs *keychain* trust, not an env var.
- A `Decision:` line lists the exact env set AC-0023 must inject + confirms git-over-SSH
  unsupported — **below**.

## Decision

Decision: AC-0023 (WP-4.2) injects, for the caged agent, the proxy + belt-and-suspenders CA
env set below; `go` is covered by keychain CA trust (not env), so `setup` must install the
CA in the keychain for `go` to work; `git`-over-SSH stays unsupported.

**Exact env set AC-0023 injects** (`P` = the project's proxy port, host `127.0.0.1`):

```sh
# Proxy routing — set BOTH cases for max tool compatibility (uppercase sufficed in
# testing; lowercase is cheap insurance for tools that only read lower-case).
HTTPS_PROXY=http://127.0.0.1:P   https_proxy=http://127.0.0.1:P
HTTP_PROXY=http://127.0.0.1:P    http_proxy=http://127.0.0.1:P
NO_PROXY=localhost,127.0.0.1,::1 no_proxy=localhost,127.0.0.1,::1   # don't proxy loopback host-services

# CA trust (env path) — covers claude/npm (Node), pip (Python), git
SSL_CERT_FILE=<mitmproxy-ca.pem>          # OpenSSL/Python/git
REQUESTS_CA_BUNDLE=<mitmproxy-ca.pem>     # Python requests / pip
NODE_EXTRA_CA_CERTS=<mitmproxy-ca.pem>    # Node / Claude Code / npm
GIT_SSL_CAINFO=<mitmproxy-ca.pem>         # git over HTTPS
```

- **`go` is NOT covered by the env CA.** It requires the mitmproxy CA in the login/System
  keychain. `agent-creance setup` installs it by default, so this is satisfied on the
  normal path. **`setup --no-ca-install` (env-only) is incompatible with `go`** — `doctor`
  should detect "CA not in keychain" and warn that `go` egress will fail (sibling to the
  S2 keychain-unlock pre-flight). No `GOPROXY`/`GOSUMDB` env tweak is injected.
- **Egress allowlist (owned by AC-0017, flagged here):** for `go` to work end-to-end the
  baseline must allow **both `proxy.golang.org` and `sum.golang.org`**. `,direct` GOPROXY
  fallback reaches VCS hosts (e.g. `github.com`) which must also be allowlisted.
- **`git`-over-SSH stays unsupported** (confirmed by design, not retested): `git@github.com:`
  uses the SSH transport, which cannot traverse an HTTP `CONNECT` proxy. HTTPS remotes only;
  `doctor`/docs should say so. The `GIT_SSL_CAINFO` env above only helps HTTPS remotes.

## Limitations / scope of this result

- **CA trust was env-var + keychain-*absent* by design.** This spike deliberately did NOT
  install the CA in the keychain (that path is AC-0026 / WP-5.1, per S1). So the `go`
  success-through-proxy claim is *inferred* from the mechanism (go uses the system verifier;
  the CA fails only because it is absent from the keychain) and proven *negatively* (B/D),
  not demonstrated positively. AC-0026's integration test should confirm `go get` succeeds
  through the proxy once the CA is keychain-installed. Everything else (`claude`/`npm`/`pip`/
  `git`) was demonstrated positively end-to-end.
- **Lightweight commands only.** `npm view` / `pip download --no-deps` / `git ls-remote` /
  `go list -m -versions` exercise the registry/proxy fetch path but not a full transitive
  `npm install` / `pip install -r` / `go mod download` (which fan out to many hosts and, for
  `go`, the checksum DB). The proxy-honoring behavior is per-process, so it generalizes, but
  the **allowlist breadth** (every transitive host) is a separate concern owned by AC-0017.
- **`go`'s `SSL_CERT_FILE`-ignored result is macOS-specific** (Go's darwin platform
  verifier). Not a portability claim; agent-creance is macOS-only anyway.
- **`ALL_PROXY` not tested** and not required by any tool here; omitted from the injected
  set. Lower-case proxy vars were not individually exercised (uppercase was) but are
  recommended as cheap insurance.

## Design impact

The design's premise — the toolchain honors `HTTPS_PROXY`, with CA trust via the
belt-and-suspenders env vars — is **validated for `claude`/`npm`/`pip`/`git`** and needs one
correction for `go` (for the gated build tickets, not this spike):

1. **`go` CA trust (around line 427).** The "belt-and-suspenders env vars
   (`NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`, `GIT_SSL_CAINFO`)" sentence
   should note that **`go` is not covered by any of these on macOS** — it trusts the CA only
   via the system keychain. The keychain install (design line 427) is therefore *required*
   for `go`, and `setup --no-ca-install` (line 357) must be documented as breaking `go`
   egress.
2. **`go` allowlist note.** `docs/design.md` should record that `go` needs both
   `proxy.golang.org` and `sum.golang.org` allowlisted (or `GOSUMDB=off`), and that
   `HTTPS_PROXY` alone suffices for routing (no `GOPROXY` rewrite).
