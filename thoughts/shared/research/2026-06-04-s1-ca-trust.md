# Spike S1 — CA trust / certificate pinning

**Decision: `api.anthropic.com` ships as a host-wide `intercept` rule (TLS-terminated, audited).**
Interception validates end-to-end against the trusted mitmproxy CA — both a raw
`curl` probe and a real Claude Code inference call (`POST /v1/messages`) succeed through
the proxy with the CA trusted. No host on the v0.1 baseline pinned. Passthrough is **not**
needed for any baseline host, so `docs/design.md` needs no fallback composition change; the
only design edit is recording this resolution (S1 → intercept).

## Question

Does the agent and its toolchain accept mitmproxy's CA for TLS interception of the v0.1
baseline hosts? If Claude Code pins `api.anthropic.com`, or `npm`/`pip`/`git` pin their
registries, MITM fails and that egress path breaks. The outcome decides the shipped default
enforcement mode for `api.anthropic.com` (`intercept` vs `passthrough`) — see
`docs/design.md` "Per-host enforcement modes".

## Environment

| Tool | Version |
|---|---|
| mitmproxy / mitmdump | 12.2.3 (Python 3.14.4, OpenSSL 3.5.5) |
| curl | 8.7.1 (LibreSSL 3.3.6, macOS system curl) |
| claude (Claude Code) | 2.1.162 |
| OS | macOS (Darwin 25.5.0), arm64 |

CA freshly generated by the first `mitmdump` run at `~/.mitmproxy/mitmproxy-ca-cert.pem`
(no prior `~/.mitmproxy/` existed). **The CA was NOT installed into the login keychain** —
trust was supplied purely via the CA-bundle env vars + `curl --cacert`, which is the
belt-and-suspenders path agent-creance also uses (`SSL_CERT_FILE`, `REQUESTS_CA_BUNDLE`,
`NODE_EXTRA_CA_CERTS`, `GIT_SSL_CAINFO`). This is the more conservative test: if it
validates without system-wide trust, it validates with it too.

## Reproduction

1. Start a proxy (first run generates the CA):

   ```sh
   mitmdump -p 18080            # CA written to ~/.mitmproxy/
   ```

2. Trust the CA via env (the agent-creance set) and probe each host through the proxy:

   ```sh
   CA=~/.mitmproxy/mitmproxy-ca-cert.pem
   export SSL_CERT_FILE=$CA REQUESTS_CA_BUNDLE=$CA NODE_EXTRA_CA_CERTS=$CA GIT_SSL_CAINFO=$CA
   curl -sS -o /dev/null --cacert "$CA" -x http://127.0.0.1:18080 \
        -w '%{http_code} %{ssl_verify_result}\n' https://<HOST>/
   ```

   `ssl_verify_result 0` + a non-zero HTTP code ⇒ interception validated; a TLS handshake
   error ⇒ the host pinned / rejected the MITM'd connection.

3. Drive Claude Code through the proxy:

   ```sh
   export HTTPS_PROXY=http://127.0.0.1:18080 NODE_EXTRA_CA_CERTS=$CA SSL_CERT_FILE=$CA
   claude --version
   claude -p "Reply with exactly one word: pong"
   ```

## Results — per host

| Host | HTTP code | `ssl_verify_result` | curl exit | Verdict |
|---|---|---|---|---|
| `api.anthropic.com` | 404 | 0 | 0 | **PASS** (404 is just "no resource at `/`") |
| `registry.npmjs.org` | 200 | 0 | 0 | **PASS** |
| `pypi.org` | 200 | 0 | 0 | **PASS** |
| `files.pythonhosted.org` | 200 | 0 | 0 | **PASS** |
| `github.com` | 200 | 0 | 0 | **PASS** |
| `codeload.github.com` | 301 | 0 | 0 | **PASS** |
| `raw.githubusercontent.com` | 301 | 0 | 0 | **PASS** |

Every baseline host: cert chain validated against the trusted mitmproxy CA, request
completed, no handshake failure. **No host pinned.**

## Results — Claude Code through the proxy

- `claude --version` → `2.1.162` (no API call; control).
- `claude -p "Reply with exactly one word: pong"` → printed `pong`, **exit 0**.
- The mitmproxy flow log confirms the call was **TLS-terminated and decrypted** by the
  proxy (full request paths visible, not just CONNECT tunnels):
  - `POST https://api.anthropic.com/v1/messages?beta=true` → `200 OK 579b` — the actual
    inference call.
  - Numerous startup calls intercepted cleanly: `/api/oauth/account/settings`,
    `/v1/mcp_servers`, `/api/claude_cli/bootstrap`, `/mcp-registry/v0/servers`, etc.

**Claude Code does not pin `api.anthropic.com`.** OAuth-bearing requests and the inference
endpoint both traverse the intercepting proxy successfully with the CA trusted via
`NODE_EXTRA_CA_CERTS`.

## Decision

Decision: ship `api.anthropic.com` as a host-wide `mode: intercept` rule in the global
baseline. Interception works against the real Claude Code client, so we keep the channel
**audited** rather than dodging a pin that does not exist. This follows the design's stated
rule ("if interception works, ship it as a host-wide `intercept` rule so the channel stays
audited"). The change lands in the global-baseline config (AC-0017 / baseline ticket), not
here — this spike only records the decision.

## Answers to the ticket's open questions

- **"If `api.anthropic.com` pins, does passthrough-at-CONNECT still let refresh + normal API
  calls through cleanly?"** — Moot. It does not pin; interception validates including the
  OAuth/settings calls and `/v1/messages`. Passthrough is not required for Anthropic.
  Consequence for the build: the `passthrough` path in WP-3.1 (AC-0017) stays an
  **optional** feature, **not** load-bearing for the headline run — this resolves the risk
  flagged in the v0.1 spec §14 ("If S1 shows pinning, `api.anthropic.com` ships passthrough
  and WP-3.1's passthrough path becomes load-bearing").
- **"Do any registries pin in a way that requires per-host passthrough rather than global
  trust?"** — No. All registry / forge hosts validated under a single globally-trusted CA;
  no per-host passthrough is needed. **Caveat (see Limitations):** this was measured with
  `curl`, not the native `npm`/`pip`/`git` clients; their proxy + pin behavior is confirmed
  separately by S4 (WP-0.4, AC-0019).

## Limitations / scope of this result

- **`curl` is not a pin test for the native clients.** `curl` validates against whatever CA
  bundle it is given and does not pin these hosts, so a `curl` PASS proves *mitmproxy can
  intercept the host and the host tolerates the proxied/MITM'd TLS connection* (no WAF
  rejection of mitmproxy's TLS, no client-cert requirement) — it does **not** by itself
  prove that `npm`/`pip`/`git` won't pin. For `api.anthropic.com` the authoritative pin test
  *is* the real Claude Code run above (PASS). For npm/PyPI/GitHub, the native-client
  behavior is owned by **S4 (AC-0019)**; this spike establishes only the CA-trust /
  host-tolerance baseline, which is its charter.
- **CA trust was env-var only**, not keychain-installed. The keychain-install + live-verify
  path is **AC-0026 (WP-5.1)**; the silent-cancel failure mode of `security add-trusted-cert`
  is out of scope here.

## Incidental findings (for the baseline-config / AC-0017 ticket)

- Claude Code also contacts **`mcp-proxy.anthropic.com`** during startup
  (`POST /v1/mcp/...`), which is **not** on the AC-0001 baseline host list. If the baseline
  is `intercept`-only and MCP-proxy traffic must work, the global baseline likely needs an
  allow rule for `mcp-proxy.anthropic.com` too (it intercepts fine — `200 OK` / `202` seen).
  Flagging for the baseline ticket; out of scope for S1's decision.

## Design impact

No architectural fallback is required (interception works, nothing pins), so no composition
change to `docs/design.md`. The S1 bullet in "Open spikes" is updated to record the
resolution and point here. The acceptance criterion that mandates a design edit is
conditional on a `passthrough` decision or a pinning host on the critical path — neither
occurred.
