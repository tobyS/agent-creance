# Research: UX audit for shell engineers using Claude Code

**Date**: 2026-06-25T13:55:59Z
**Git Commit**: 64d2d7b580211e2ceba6748873313df9f9eef930
**Branch**: main
**Repository**: agent-creance

## Research Question

Audit the project's user experience for the target audience — software
engineers who work on the shell and use Claude Code. How easy is it for them to
use the tool? Be critical about the UX, with usability improvements in focus.

> **Scope note.** This is an explicit critique/improvement audit requested by the
> user, so — unlike a normal `/tce:research` document — it evaluates and proposes,
> it does not only describe. Findings are evidence-backed (file:line) and the
> proposals are options for the planning phase, not decisions.

## Summary

The tool's **internals are more polished than its surface**. The runtime
presentation layer (color/TTY/`NO_COLOR` handling, stderr/stdout discipline,
progress rendering, glyph-identifiable-without-color output) is genuinely
well-built, and the *agent-facing* UX (the cage briefing + skill that teach
Claude how to react to 470/471 refusals) is thoughtful. The host-side **error
messages are two-tier**: the deliberate precondition refusals (missing tools,
incomplete setup, unreachable credential) are excellent and actionable, but a
second tier of mid-startup and config-validation errors are bare technical
wraps with no remediation.

The weakest area by far is **first contact**: there is no quickstart, the README
status banner is stale and self-contradicting, there is no documented install
path, `--help` is nearly empty for every command (only `include` has a `Long:`,
nothing has an `Example:`), and the single most natural first action — typing
`agent-creance run` in a fresh repo — dead-ends on a bare `file not found`
instead of pointing at `init`. A shell engineer who lives in `--help` and
trial-and-error hits friction before reaching the well-built core.

## What works well (so the critique is fair)

- **Precondition refusals are model-grade.** `run` gates on prerequisites,
  setup, and credential state *up front* with actionable, command-bearing
  messages instead of failing deep in the stack (`internal/cli/run.go:56-85`;
  `internal/prereq/prereq.go:157-168`; `internal/setupcheck/setupcheck.go:83-90`;
  `internal/cred/cred.go:87-96`). The missing-tools block lists *all* missing
  tools at once with `brew` hints, so the user installs once
  (`internal/prereq/prereq.go:157-168`).
- **Presentation infrastructure is solid.** One central style layer where
  "color off == byte-identical plain output" (`internal/style/style.go:6-9`),
  per-stream TTY detection (`internal/sysdep/terminal.go:56-59`), `--color
  auto|always|never` honoring `NO_COLOR` resolved once in the root
  (`internal/cli/cli.go:98-117`), `run` progress correctly on **stderr** because
  stdout belongs to the agent (`internal/cli/run.go:93-97`), and in-place
  progress counters that degrade to milestone lines when piped/CI
  (`internal/progress/printer.go:131-152`).
- **`doctor` is a real diagnostic.** Sectioned report with version-compat table,
  per-check glyphs, and most findings carrying a fix pointer
  (`internal/doctor/report.go:118-201`; golden at
  `internal/doctor/testdata/render_healthy.golden`).
- **Agent-side UX is a strength.** The always-injected launch briefing
  (`internal/cage/briefing.md`) plus the installed skill
  (`internal/setup/SKILL.md`) tell the caged agent it is caged, what 470/471
  mean, that WebFetch hides the refusal body, and to `curl` for the structured
  refusal — and the refusal JSON itself carries `allow_command_suggestion`
  (design.md:294-308). This is the part most tools get wrong and this one gets
  right.
- **`init` chains setup for you.** Interactive `init` runs the host-setup gate
  first and offers to complete setup inline, so a user who starts at `init`
  doesn't have to know about `setup` (`internal/cli/init.go:56-61,158-197`).

## Detailed Findings (by severity)

### S1 — `agent-creance run` with no config dead-ends instead of pointing at `init`

The most natural first action for a shell engineer — install, `cd` into a
project, type `agent-creance run` — has no friendly "this project isn't
initialized; run `agent-creance init`" path. `run` checks prerequisites, setup,
and credential preconditions with actionable messages
(`internal/cli/run.go:56-85`), but a **missing `.agent-creance.yaml` is not a
precondition** — it falls through to the policy compile (step 5) and config load
(step 6), surfacing as a bare wrap:

- `compile policy: %w` (`internal/cli/run.go:111`) or `load config: %w`
  (`internal/cli/run.go:122`)
- wrapping `config: file not found: .agent-creance.yaml: <err>`
  (`internal/config/load.go:154`)

There is no mention of `init` in that path. Result: the user's first command
yields `error: load config: config: file not found: .agent-creance.yaml`, a
classic dead-end at exactly the moment a new user needs a nudge.

**Improvement options:** add a fourth precondition in `run` — if `configFile`
(`internal/cli/run.go:30`) is absent, refuse early with
`No .agent-creance.yaml in this project. Run \`agent-creance init\` to create
one.`, matching the existing precondition style (run.go:59-85).

### S2 — README status banner is stale and self-contradicting

`README.md:9-12` states: *"What's implemented today is the project skeleton plus
the `version` and `doctor` … commands."* The **same README** then documents
`setup` (README.md:21-48), `init` imports (README.md:50-79), and `import`
(README.md:74-79) in detail, and all of `setup`/`init`/`run`/`allow`/`deny`/
`import`/`policy` are implemented and tested in `internal/cli/`. A shell engineer
reads the banner first, concludes "not usable yet," and bounces — or trusts it
and never tries `run`. The `## Requirements` block compounds this:
*"For actually running a cage (not yet wired up)…"* (README.md:18).

**Improvement options:** update the banner to reflect the real implemented
surface, or drop the per-command claim and keep only a version label.

### S3 — No quickstart and no documented install path

The clone→build→`setup`→`init`→`run` happy path is never written end-to-end for
a user in one place. It exists only as:
- prose in the *design* doc's Commands section (design.md:406-475), which is not
  a getting-started guide; and
- partial in-CLI "Next:" hints (`internal/cli/init.go:140,142`).

The README has **no Getting Started / Quickstart / Install heading**. There is no
Homebrew formula (no `*.rb` in repo), no `go install` line, no release-binary
pointer — only `make build` → `./bin/agent-creance` (README.md:82-90). For a tool
whose entire pitch is "a single command," there is no documented way to get that
single command onto `PATH`. (A Homebrew tap is a v1.0 roadmap item, design.md:575.)

**Improvement options:** a README quickstart with the 4-step sequence and at
least one install method (`go install`, a `make install` to `/usr/local/bin`, or
a tap); the "(not yet wired up)" qualifier removed from Requirements.

### S4 — `--help` is nearly empty: no `Long:`, no `Example:`, no command grouping

For an audience that lives in `--help`, the in-CLI help *is* the documentation —
and it is thin:

- **Only `include` has a `Long:`** (`internal/cli/include.go:23-26`). Every other
  command — including `run`, `setup`, `init`, `doctor` — shows only its one-line
  `Short:` plus flags. `agent-creance run --help` tells the user nothing about
  prerequisites, what it does, or what to expect.
- **No command has an `Example:`** field anywhere.
- **Root has no `Long:`** (`internal/cli/cli.go:88-117`) — `agent-creance --help`
  is a one-liner plus an alphabetized command list, with no "start here" or
  recommended-sequence narrative.
- **No grouping.** 13 commands are registered (cli.go:119-132) and cobra
  alphabetizes them, so `allow, clean, deny, doctor, import, include, init,
  logs, policy, run, setup, status, version` appear flat, with no
  setup/daily/inspect/maintenance hierarchy and no signal that `setup`+`init`+
  `run` are the path.

**Improvement options:** add `Long:`+`Example:` to at least `run`, `setup`,
`init`, `allow`, `doctor`; add a root `Long:` with the happy-path sequence; use
cobra command groups (`AddGroup`/`GroupID`) to cluster them.

### S5 — `setup` vs `init` distinction has no orientation

The host-once (`setup`) vs project-once (`init`) split is a classic point of
confusion, and nothing orients the user to it. The `Short:` strings are accurate
("Trust the mitmproxy CA…" vs "Write a starter .agent-creance.yaml…",
setup.go:29 / init.go:32) but there is no overview anywhere stating "`setup` runs
once per machine, `init` once per project." `init` mitigates by chaining setup
inline (init.go:158-197), but a user starting from `setup` gets **no final
"Next: run `agent-creance init`"** pointer — `setup` prints per-step `✓` lines
and returns with no summary tying the steps together or naming the next command
(setup.go, per onboarding evidence).

**Improvement options:** a one-line "Next: `agent-creance init` in your project"
at the end of `setup`; a sentence in the root `Long:` distinguishing the two.

### S6 — Mid-startup and config errors are a bare second tier (no remediation)

The precondition refusals are excellent, but once past them the error quality
drops to raw Go wraps with no next step:

- `run` step errors: `resolve project: %w`, `init compiler: %w`,
  `compile policy: %w`, `load config: %w`, `compile profile: %w`,
  `extract enforcer: %w`, `start proxy: %w`, `resolve cage inputs: %w`
  (`internal/cli/run.go:90-183`). A failed launch shows e.g.
  `error: start proxy: <low-level>` with no "try `agent-creance doctor`" pointer
  (the proxy-crash path *does* point at doctor —
  `internal/proxy/lifecycle.go:209` — but the generic `start proxy` wrap does
  not, and the readiness-timeout `internal/proxy/lifecycle.go:215` is bare).
- **Config validation pinpoints the field but never shows the fix.** e.g.
  `egress <list> rule <n> uses mode: passthrough, which cannot carry paths`
  (`internal/config/validate.go:38`) — correct and specific, but for a
  hand-edited YAML it never shows the corrected shape or a command. The loader
  errors (`config: file not found`, `config: include not found`,
  `config: read …`) are likewise bare (`internal/config/load.go:154,212,281`);
  the include-out-of-scope error is the partial exception that names allowed
  scopes (load.go:320).

**Improvement options:** thread a phase/remediation hint into the high-traffic
`run` wraps (config + proxy at minimum) pointing at `doctor`/`init`; for the
most common config validation errors, append a one-line "valid form:" example.

### S7 — Thin machine-readability for a scripting audience

Shell engineers automate. Today `--json` exists **only** on the three `policy`
subcommands (`internal/cli/policy.go:59,89,126`); `doctor`, `status`, and `logs`
have no machine-readable mode, and there is **no `--quiet`/`--verbose`** anywhere
(verified absent). So scripting "is a cage running / is the host healthy"
(`status`/`doctor`) means parsing human tables, and a CI `run` always emits
progress (degraded, but present) with no way to silence it. `init`'s many y/N
prompts also have no global accept-all — only `import` has `--yes`
(`internal/cli/import.go`); init's imports auto-skip without a TTY, which is safe
but means they can't be opted *into* non-interactively.

**Improvement options:** `--json` on `doctor` and `status` (both already build
structured reports internally), a `--quiet` for `run`.

### S8 — Shell completion is not surfaced

For a shell-native audience, tab completion is high-value and cobra provides it
nearly free, but there is no `completion` command surfaced or documented, and no
install hint. (Not confirmed as registered; worth checking whether cobra's
default `completion` command is even reachable given the explicit
`AddCommand` list at cli.go:119-132.)

## Architecture Documentation

The CLI is a cobra tree assembled in `internal/cli/cli.go` with an injected `App`
composition root; presentation is centralized in `internal/style` with per-stream
TTY resolution in `internal/sysdep/terminal.go`. Human-facing rendering lives in
per-domain `report.go`/`render.go` files (doctor, status, prereq, policy/render,
audit), each with golden-file coverage — meaning output format changes are
testable and the proposed help/error improvements would slot into an existing,
well-tested rendering discipline rather than ad-hoc `Printf`s.

## Open Questions

- **Does `run` ever succeed without a config?** **Resolved (2026-06-27): no.**
  The project config is loaded as **required** (`compile/compile.go:224`,
  `optional=false`), in contrast to the global config which is optional
  (`compile/compile.go:220`). There is no implicit-default path. The failure also
  surfaces earlier and more cryptically than first described: at **step 5 (compile
  policy)**, not step 6, and triple-wrapped — `error: compile policy: compile:
  load project: config: file not found: .agent-creance.yaml`. Reinforces S1.
- **Is cobra's default `completion` command reachable?** **Resolved (2026-06-27):
  yes — it already exists and works.** No `CompletionOptions`/`DisableDefaultCmd`
  in `cli.go`, and the built binary lists `completion` in `agent-creance help` and
  emits a valid script for `completion zsh`. So S8 is "document + surface the
  existing command" (it's buried, alphabetized between `clean` and `deny`, with no
  install hint), **not** "enable it."
- **First-time CA trust dialog:** the macOS keychain auth dialog is titled
  "security" and `setup` pre-explains it (setup.go:218-222) — does the explanation
  survive when `setup` is reached *via* `init`'s inline gate, or only on direct
  `setup`? (Still open; affects onboarding polish only.)
