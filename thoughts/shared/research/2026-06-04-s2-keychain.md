# Spike S2 — Keychain access from inside the sandbox + concurrent refresh

**Decision: the Anthropic OAuth credential is the login-Keychain generic-password item
`Claude Code-credentials` (account = the login short name, e.g. `toby`). A
`sandbox-exec`-confined process reads AND updates it non-interactively given exactly
two allowances — `(allow mach-lookup (global-name "com.apple.SecurityServer"))` for read,
plus a file-write scoped to `~/Library/Keychains/login.keychain-db*` for the refresh
write.** No GUI-agent grant is needed; the item's ACL is **not** bound to Claude Code's
signed identity (a different binary read and wrote it without a prompt). Concurrent caged
writers are serialized by `securityd` with no corruption or deadlock — the v0.1 "single
shared item" assumption **holds**. The one non-interactive failure mode is a **locked**
login keychain, which raises a blocking GUI unlock prompt; `doctor` must detect it.

## Question

On macOS the Claude OAuth token lives in the login Keychain, not a file. Can a
`sandbox-exec`-confined process read and refresh the specific Anthropic Keychain item
without an interactive prompt or denial, and do two concurrent caged sessions sharing the
one item corrupt each other's refresh-token rotation? The exact service/item name and the
minimal Seatbelt rules are unknown and must be pinned down — they are what AC-0014's
profile compiler and AC-0022's credential detection will encode. See `docs/design.md`
"The proxy and the credential story" and "Open spikes" (S2).

## Environment

| Tool | Version |
|---|---|
| macOS | 26.5 (build 25F71), Darwin 25.5.0, arm64 |
| security | system `/usr/bin/security` (legacy `SecKeychain` CLI) |
| sandbox-exec | system `/usr/bin/sandbox-exec` (Seatbelt) |
| claude (Claude Code) | 2.1.162 |

The login keychain (`~/Library/Keychains/login.keychain-db`) was unlocked (the normal
post-login state) for all read/write tests except the dedicated locked-keychain probe,
which used a throwaway keychain so the real login keychain was never locked.

## The Keychain item (exact identity)

Located with `security find-generic-password -s "Claude Code-credentials"` (attributes
only; the secret was never printed):

| Attribute | Value |
|---|---|
| keychain | `~/Library/Keychains/login.keychain-db` (login keychain) |
| class | `genp` (generic password) |
| `svce` (service) | `Claude Code-credentials` |
| `acct` (account) | the login short name (`toby` here) = `$(id -un)` |
| lookup key | **service name alone is unique** — `-s "Claude Code-credentials"` returns exactly one item; account is the disambiguator if ever needed |

The secret value is JSON (~471 bytes) with a single top-level key `claudeAiOauth`:

```
claudeAiOauth: { accessToken, refreshToken, expiresAt, scopes, subscriptionType, rateLimitTier }
```

`accessToken`/`refreshToken` are ~108-char strings; `expiresAt` is an epoch-ms timestamp
(observed lifetime ≈ 8 h). This confirms the design's premise: the credential is a single
shared Keychain item, not a file, and refresh rotates the `refreshToken` in place.

## Reproduction & results

### 1. Non-interactive READ from inside the sandbox — **PASS**

Three profiles, identical except for the keychain allowance, running
`sandbox-exec -f <profile> security find-generic-password -s "Claude Code-credentials" -a <user> -w`
under an 8 s watchdog (so a blocking GUI prompt cannot hang the run). Secret captured to a
variable; only exit code + byte length reported.

| Profile | mach-lookup `SecurityServer`? | Result |
|---|---|---|
| `(allow default)` (control) | — | **PASS** exit 0, 472 B, 1 s |
| restrictive + `SecurityServer` | yes | **PASS** exit 0, 472 B, 1 s, **no GUI prompt** |
| restrictive − `SecurityServer` | no | **FAIL** exit 44, `SecKeychainSearchCopyNext: item could not be found` |

The minimal read profile:

```scheme
(version 1)
(deny default)
(allow process-fork) (allow process-exec) (allow sysctl-read)
(allow file-read* file-read-metadata)
(allow file-write-data file-write-flags (subpath "/private/tmp") (subpath "/private/var/folders"))
(allow mach-lookup (global-name "com.apple.SecurityServer"))   ; <-- necessary AND sufficient
```

`com.apple.security.agent` (the GUI-prompt service) was **not** granted, yet the read
succeeds — proving the access is non-interactive. The negative control (no `SecurityServer`
mach-lookup) cannot even reach `securityd`, so the item is reported "not found" — confirming
the mach-lookup is the load-bearing read requirement (the cage's normal `file-read*` to the
keychain db is not sufficient on its own).

### 2. Non-interactive REFRESH (keychain write/update) from inside the sandbox — **PASS** (needs a file-write grant)

Refresh = read old token → HTTPS call to the token endpoint → **update** the item with the
rotated token. The HTTP half is a plain call to the allowlisted Anthropic token endpoint
through the proxy (validated by S1). The keychain half is an `SecItemUpdate` /
`SecKeychainItemModifyContent`. Tested safely by writing the item's **current value back
unchanged** (`security add-generic-password -U … -w "$current"`) so the real credential is
never altered — integrity verified by SHA before/after each run.

| Profile | Result |
|---|---|
| read profile (mach-lookup only, no kc write) | **FAIL** exit 161, `SecKeychainItemModifyContent: UNIX[Operation not permitted]` |
| + `file-write*` to `~/Library/Keychains` (whole dir) | **PASS** exit 0, 1 s, value preserved |
| + `file-write*` regex `^…/Library/Keychains/login\.keychain-db` (least-privilege) | **PASS** exit 0, 1 s, value preserved |

The read path is brokered entirely by `securityd`, but the **legacy `SecKeychain` modify
path writes the keychain db file directly** (atomic create+rename+unlink of
`login.keychain-db` and its SQLite `-wal`/`-shm` sidecars), so it needs file-write to those
paths. This matters because **`security` and node `keytar` both use the legacy
`SecKeychain` family** — so a real Claude Code refresh (if keytar-backed) needs the same
grant. The grant can be scoped to the login keychain db + sidecars (regex above); the whole
`~/Library/Keychains` directory is not required. No GUI prompt in any passing case.

### 3. Concurrent refresh — **no corruption, no deadlock; assumption holds**

Two overlapping `sandbox-exec` writers performing the safe identical-value update against
the one shared item, run twice:

| Run | Writer A | Writer B | Item after |
|---|---|---|---|
| 1 | exit 45 `item already exists` | exit 0 | **intact + readable** |
| 2 | exit 0 | exit 45 `item already exists` | **intact + readable** |

`securityd` **serializes** the writers: one wins, the other gets a transient, benign
"already exists" race error (an artifact of the CLI's add-then-modify two-step) that a
normal client simply retries. No partial write, no corruption, no hang — total time 1 s.
This is **identical to two un-caged `security` writers**; the cage introduces no new failure
mode. The store itself is the synchronization point, exactly as `docs/design.md` argues
(line 440). The v0.1 **"single shared item" assumption holds.**

### 4. Locked-keychain failure mode (for `doctor`) — blocking GUI prompt

Characterized safely with a throwaway keychain (the real login keychain was never locked):

| State | Sandboxed read |
|---|---|
| unlocked | **PASS** exit 0 |
| **locked** | **blocking GUI unlock prompt** (watchdog timed out at 8 s) |

A locked keychain does **not** fail cleanly — `securityd` raises the SecurityAgent unlock
dialog out-of-process (so it appears even though the cage never gets the
`com.apple.security.agent` service). The login keychain is normally auto-unlocked at login,
so this is an edge case (manual lock, or an auto-lock-on-sleep/idle setting), but it is a
real non-interactive failure mode the cage cannot recover from. **`doctor` and `run`
must verify the login keychain is unlocked before launching a caged session** and refuse
with a clear message rather than letting the session hang on an invisible prompt.

## Answers to the ticket's open questions

- **"Does the Keychain ACL need the caged binary to be the same signed identity as host
  Claude Code?"** — **No.** `/usr/bin/security` (a different binary from the node Claude
  Code process that created the item) both **read and updated** the item non-interactively.
  The item's ACL is not bound to Claude Code's code signature; access is gated by
  `securityd` reachability (the mach-lookup) plus the keychain's unlock state, not by the
  caller's identity. AC-0014 therefore does not need to match or impersonate Claude Code's
  signed identity — granting the mach-lookup (+ kc-db write for refresh) is enough.
- **"Is there a non-interactive failure mode (locked keychain) we must detect in
  `doctor`?"** — **Yes** (see §4). Locked keychain → blocking GUI prompt. `doctor`/`run`
  must pre-flight the unlock state.

## Decision

Decision: the cage reads the Anthropic OAuth token from the login Keychain item
`Claude Code-credentials` via `mach-lookup com.apple.SecurityServer`, and refreshes it with
an added file-write to `~/Library/Keychains/login.keychain-db*`; detection keys off that
service name, and `doctor`/`run` pre-flight the keychain unlock state. Details:

- **Item:** the Anthropic OAuth credential is the login-Keychain generic-password item with
  service `Claude Code-credentials`, account = the login short name (`$(id -un)`). Service
  name is the unique lookup key.
- **AC-0014 (Seatbelt profile)** grants the cage exactly:
  - `(allow mach-lookup (global-name "com.apple.SecurityServer"))` — required for read;
  - `(allow file-write* (regex #"^<HOME>/Library/Keychains/login\.keychain-db"))` — required
    for the refresh write (legacy `SecKeychain`/keytar path). `<HOME>` is templated per user.
  - No `com.apple.security.agent` grant; access is non-interactive by design.
- **AC-0022 (credential detection)** keys detection off the service name
  `Claude Code-credentials`; "Keychain item absent **but** `~/.claude/.credentials.json`
  present" remains the file-fallback **refuse** case (file creds out of scope for v0.1).
- **`doctor`/`run`** verify the login keychain is **unlocked** before a caged run (locked →
  refuse with a clear message; do not let the session hang on an invisible unlock prompt).
- **Concurrency:** keep the single shared item (no per-project cloning); `securityd`
  serialization makes concurrent refresh no worse than two un-caged sessions.

## Limitations / scope of this result

- **Write path tested with the `security` CLI (legacy `SecKeychain` API), not a live Claude
  Code OAuth rotation.** A real token expiry/refresh was not forced (the token was valid for
  ~8 h). The identical-value update exercises the same `SecItemUpdate`/`SecKeychainItemModify`
  ACL + file-write code path, and keytar uses the same legacy family, so the requirement is
  well-founded — but AC-0022/AC-0014 should confirm against a real caged refresh once the
  credential plumbing exists. If Claude Code ever moves to the modern data-protection
  keychain (securityd-mediated writes), the `login.keychain-db` file-write grant may become
  unnecessary; the mach-lookup would still be required.
- **The keychain-db file-write grant is broader than the design's "item's ACL" framing.**
  `docs/design.md` (line 436) assumed item-level ACL granularity; in practice the legacy
  write path needs **file-level** write to `login.keychain-db`, which lets the cage write
  the keychain database file (logical per-item access is still mediated by `securityd` +
  per-item ACLs, but raw file writes are possible). This is the minimum that makes in-cage
  refresh work; the only way to avoid it would be to broker the refresh write host-side
  (a v0.2-style design change, out of scope for v0.1). Flagged for AC-0014's threat-model
  note.
- **Secret hygiene:** token values were never printed (captured to shell variables; only
  lengths/hashes reported). The brief argv exposure of the secret to `security` during the
  identical-value write round-trip is the same exposure the un-caged client already has and
  is self-only on this machine.

## Design impact

The design's credential model (single shared Keychain item, in-cage read + refresh, no
per-project cloning) is **validated** — no architectural change. Two documentation updates
are warranted (for the relevant build tickets, not this spike):
1. The Seatbelt grant is **mach-lookup `com.apple.SecurityServer` + a file-write to
   `login.keychain-db*`**, not merely "the item's ACL" as line 436 currently implies.
2. `doctor`/`run` gain a **keychain-unlocked pre-flight** (line 444's CA verification is the
   analogous existing pattern; this is a sibling check).
